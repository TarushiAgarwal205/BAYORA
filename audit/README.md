# SQLite audit storage

Audit events are stored by `backend/audit_store.py`. The SQLite event schema is preserved and extended with additive initialization where needed; hash snapshots live in separate `audit_integrity` and `audit_integrity_meta` tables.

Policy decisions start as `NOT_EXECUTED` and `NOT_VERIFIED`. Resource and LLM operations are recorded as pending, then finalized with an observed outcome. Ambiguous failures remain `UNKNOWN` and `NOT_VERIFIED`. Session IDs are caller-supplied correlation labels scoped by the authenticated role. Reusing an ID under another role does not change caller authority or create a cross-role session binding. Shared role credentials do not identify individual users, so these labels do not provide per-user session isolation.

`GET /audit/integrity` and the dashboard-compatible `GET /audit/verify` verify the append-only SHA-256 snapshot revision chain against a persistent authenticated checkpoint stored outside the audit SQLite database. Event and detail APIs, anomaly findings, and evidence summaries are scoped to the authenticated caller role. Reports omit Red-run files because those files do not currently carry authenticated role ownership metadata.

The revision chain is unkeyed SHA-256; the independent checkpoint is authenticated with HMAC-SHA-256 using `BAYORA_AUDIT_CHECKPOINT_KEY` (minimum 32 bytes). While the checkpoint and key remain intact, the checkpoint detects a rewritten chain head, including paired deletion of the newest event and matching chain entry. The checkpoint uses a separate SQLite file; Compose persists it in a named volume separate from `/app/data`. Local development defaults to a sibling file beside the audit DB, so deployments should use separate protected storage when those files have different threat exposure.

This does not protect against a compromised Gateway process or host administrator, both of which can access the key and checkpoint. It also cannot detect restoration of a matching older audit-database/checkpoint backup pair or establish the truth of legacy history before the checkpoint was created. No event is described as verified unless the resource response is checked against configured synthetic fixture evidence.

The Gateway serializes audit writers across local processes. Each SQLite revision commits before the checkpoint performs an atomic compare-and-set of exactly one sequence. A lost acknowledgement is resolved by reading the checkpoint and confirming the same operation ID and revision. If the DB commit succeeds but checkpoint advancement does not, the chain is one revision ahead; reads/writes fail closed. Explicit `python -m backend.audit_checkpoint_cli recover --approve-unanchored-revision` recovery can anchor only one locally valid next revision after operator review. Missing, stale, mismatched, or unavailable checkpoints are not silently re-created. Existing stores without a checkpoint must be explicitly bootstrapped with `python -m backend.audit_checkpoint_cli bootstrap --approve-current-history`; this trusts only the current history and cannot detect prior truncation.

Backups must include the audit DB, checkpoint volume/file, and HMAC key from a coordinated, quiescent state. Stop the Gateway before copying or restoring them, and restore all three together. A stale/mismatched pair remains unavailable until a known consistent set is restored or an operator reviews the single-revision recovery case.

Audit-store tests use temporary SQLite databases and checkpoint files. They cover event persistence, state transitions, paired tail truncation, event modification, interior deletion, reordering, checkpoint mismatch/unavailability, idempotent retries, concurrent writers, interrupted writes, explicit recovery, and fail-closed behavior when initialization metadata is missing.

Administrator policy/configuration changes and scenario runs use pending-operation events, then store the final outcome and metadata in the integrity-chained event revision. Prompt inspection evidence stores only outcome, rule identifiers, severity, length, and SHA-256 digest; prompt text is not put in the audit database. The separately authenticated incident workspace can search all roles; the existing caller audit APIs remain role-scoped.
